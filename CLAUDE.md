# Borrowed Compute

Run code jobs (builds, tests, scripts, small ML training) on another computer of yours, in any direction: Windows to Mac, Mac to Windows, Windows to Windows, Mac to Mac. One app per OS both uses other devices and lends its own. The sender sends **source plus a job spec**; the lender runs its own native toolchain and streams output back. No binaries cross between machines.

Product and design docs live outside this repo, in the parent folder `../`: `Borrowed Compute Foundation.md` (locked v1 decisions, scope, milestone) and `Q1`–`Q6` (toolchains, sync, latency, sandbox, ML stack, legal). Read the Foundation doc before changing scope or architecture.

## Layout

| Path | What |
|---|---|
| `crates/bc-proto` | `bc.toml` spec (`spec.rs`), device-to-device CBOR frames (`wire.rs`), cloud JSON bodies (`cloud.rs`). No networking. |
| `crates/bc-net` | iroh endpoint setup, device key files, `send_msg`/`recv_msg` over QUIC streams, `lan.rs` (Macs on the local network over mDNS) |
| `crates/bc-secrets` | Device key and session token storage: OS keychain (macOS Keychain, Windows Credential Manager) when a program calls `bc_net::use_keychain()` at startup, migrating old files in; owner-only files otherwise, which is what libraries and tests use |
| `crates/bc-infer` | Borrowed Compute's own inference engine (`docs/mesh.md` §4): `gguf.rs` (header parser, test writer), `quant.rs` (ggml block formats, int8 integer products), `pool.rs` (work-stealing threads, `BC_INFER_THREADS`), `model.rs` (Llama/Qwen2 transformer a layer range at a time, KV cache per conversation), `tokenizer.rs` (SentencePiece and byte-level BPE, chat templates), `sample.rs`, `source.rs` (GGUF by byte range into memory, https or loopback http only from other devices), `gpu/` (whole layers on the GPU: Metal on a Mac, CUDA elsewhere, one C kernel source `kernels.h`; after editing it or `cuda.cu` run `gpu/build-ptx.sh` to rebuild `kernels.ptx`, which needs Homebrew's llvm; `BC_INFER_GPU=0` turns the GPU off, `=debug` says why it is not used). `cargo run -p bc-infer --release --example generate -- <gguf> "<prompt>"` checks a real model whole and split |
| `crates/bc-mesh` | Several devices as one (design: `docs/mesh.md`): `probe.rs`, `plan.rs` (layer placement, ring order, replicas, catalog, `replan` with hysteresis), `ticket.rs`, `codec.rs`, `stage.rs` (device side), `pipeline.rs` (coordinator side), `engine.rs` (LLM stages on a lender: weights by range into RAM, dropped 2 minutes after the last stage), `llm.rs` (requests over pipelines; the coordinator can hold the first stage itself, run in-process before anything crosses the network, chunked prefill, speculative decoding, pipelined: a batch of guesses per stage in flight for a lone conversation, dropped by epoch on a miss). `bc mesh probe/plan/run/serve` in the CLI (`bc_cli::mesh`, `bc_cli::serve` for the OpenAI-compatible endpoint); the desktop app's Mesh page (`src/mesh.rs`, `ui/mesh.js`) |
| `crates/bc-auth` | HTTP client for `bc-cloud`, session file storage |
| `apps/bc-agent` | Mac agent: `runner.rs` (workspace, process, output), `server.rs` (per-connection protocol), `paired.rs` (allowlist), `guests.rs` (invited devices on other accounts), `cloud_sync.rs` (heartbeat + paired list), `service.rs` (the running agent, shared by `bc-agent serve` and the menu-bar app), `services.rs` (jobs run as services: owned by the agent, not the connection), `events.rs` (job and sync events for a UI) |
| `apps/bc-cli` | `bc` binary: `pack.rs` (tar of project), `run.rs` (client side of a job), `detect.rs` (project type and suggested commands), `forward.rs` (service ports to this computer's localhost), `autofix.rs` (installs or builds what the upload left out before a run; after a failed run, recognizes a missing module, command or build file and runs once more with the fix), `flows.rs` (steps shared with the desktop app: resolve Mac, load spec, split command, wait for pairing), `shared.rs` (joining a Mac through an invite, and the device's list of shared Macs), `main.rs` (commands) |
| `apps/bc-desktop` | The Tauri 2 app ("Borrowed Compute"), on Mac and Windows: it uses other devices (`src/main.rs`: pick a device, send a folder, stream output) and lends this one (`src/lend.rs`: runs `bc_agent::service::Agent`, pairing approval, guests, recent jobs, and `bc-cloud` on SQLite when the account lives on this device, shared over iroh by `bc_net::cloud`). `ui/` is plain HTML/CSS/JS: `app.js` (sign-in, devices, runs) and `lend.js` (the "This device" pages, in its own scope). A normal Dock or taskbar app; with Run in background on, quitting only hides it (`src/quit_guard.rs` adds `applicationShouldTerminate:` on macOS, which Tauri lacks) and a menu-bar or tray icon reopens it. One home per device (`device_home`): `<config>/BorrowedCompute/agent` on a Mac (where the old Mac app kept it), `…/cli` elsewhere (shared with `bc`), so existing installs keep their key, session and pairings. Per-OS config: `tauri.macos.conf.json` keeps the old Mac app's identifier and `agent.json` feed, the base config the Windows app's and `client.json`, so installed copies of both old apps update into this one. |
| `website/` | Public site at https://borrowed-compute.vercel.app (static HTML, CSS, JS on Vercel). Edit `src/*.html` and `partials/`, run `python3 website/build.py`, deploy with `vercel deploy --prod` inside `website/`. The site uses the app's ink and Geist language; the hero is a replica of the app replaying a real run, with the lending computer's cores heating ink to yellow to red (`site.js`), and Cmd/Ctrl+K opens a jump-to palette; add `?still` to any page for a settled, motion-free view. Release notes come from `/api/releases` (a Vercel function reading the public feed) plus `api/notes.json`. |
| `design/` | Icon sources (SVG). Regenerate with `npx @tauri-apps/cli@2.12.4 icon design/icon-client.svg -o apps/bc-desktop/icons` |
| `apps/bc-cloud` | axum + sqlx `Any`: GitHub device-flow sign-in, devices, pairings, presence. Runs on SQLite (inside the Mac app) or Postgres. Migrations in `migrations/sqlite` and `migrations/postgres` |

## Commands

```bash
cargo test --workspace
cargo clippy --workspace --all-targets
```

Cloud API tests always run on a fresh SQLite file; with `BC_TEST_DATABASE_URL` set they also run on Postgres (each test creates its own database):

```bash
BC_TEST_DATABASE_URL=postgres://bc@127.0.0.1:54329/postgres cargo test --workspace
```

Throwaway local Postgres (Homebrew): `initdb -D <dir> -U bc --auth=trust`, then start with `LC_ALL=en_US.UTF-8 pg_ctl -D <dir> -o "-p 54329 -k /tmp/bcpg -h 127.0.0.1" start`. Postgres refuses to start without `LC_ALL`, and Unix socket paths over 103 bytes fail, hence `-k /tmp/bcpg`.

Desktop app: `cargo run -p bc-desktop` for development (the UI is static files in `ui/`, no bundler). Bundles: `npx @tauri-apps/cli@2.12.4 build` inside the app's folder (`--debug --bundles app` for a quick macOS `.app`). The UI is embedded at compile time, so rebuild after editing `ui/`. For a `.dmg`, run with `CI=true` so the bundler skips its Finder AppleScript styling, which times out without automation permission. Release builds rely on `[profile.release.build-override] strip = false` in `Cargo.toml`; without it, macOS 27 fails every release build with "mis-aligned LINKEDIT string pool".

Run the cloud on its own: `BC_DATABASE_URL=postgres://… or sqlite://<file>?mode=rwc BC_GITHUB_CLIENT_ID=... cargo run -p bc-cloud` (listens on `127.0.0.1:8080`). Normally the Mac app hosts it. A device's cloud address is `BC_CLOUD_URL`, else the `cloud-url` file in its home folder (set by the apps or `bc cloud <address>`), else `http://127.0.0.1:8080`. `BC_HOME` relocates keys, sessions, the cloud address and the Mac app's `cloud/cloud.db`.

## Releases and updates

Every merge to `main` runs `.github/workflows/release.yml`. The app's Mac build (agent, the old Mac app's name) and Windows build (client) are **versioned separately** (the merged app starts at 0.3.0 on both): `.github/release-plan.sh` compares the push with each app's last tag in this repo (`agent-v0.2.3`, `client-v0.2.7`; both start at 0.2.0) and releases only the apps whose files changed (shared crates and toolchain files release both). Each built app is signed and published to the public repo `Harshil089/Borrowed-Compute-releases` as its own release (`agent-v…` with the dmg, `client-v…` with the installer), then this repo is tagged. Every release carries both `agent.json` and `client.json` (the other app's copied from the previous latest release), because each app's Check for updates reads its manifest from the releases repo's latest release. Run the workflow by hand with `apps: both|agent|client` to force a release. Each app installs only packages signed by the key whose public half is `plugins.updater.pubkey` in its `tauri.conf.json`. The private key is the `TAURI_SIGNING_PRIVATE_KEY` secret (local copy `~/.tauri/borrowed-compute-updater.key`); publishing uses the `RELEASES_TOKEN` secret. Losing the key means installed apps can never update again; reinstall by hand with a new key. Install and restart (`download_update` in each app) downloads up to 4 times, starting again after a dropped connection or 45 seconds with no data, and sends `update-progress` events for the window's progress bar; a bad signature is not retried. On the Mac the app then exits and opens the new version only once the old process is gone (`relaunch_after_exit`, killing it after 20 seconds), because Tauri's `restart` overlapped the two and left the new window blank. Both apps also install a newer release by themselves when they start (`updateOnStart` in each `ui/app.js`), so an old installer never leaves anyone on an old version; versions `0.1.0` (local builds) skip this. On Windows the updater starts the installer and exits the app at once; `apps/bc-desktop/windows/hooks.nsh` waits for the app to close and force-closes it after 10 seconds, because Tauri's own check otherwise stops with "Failed to kill Borrowed Compute", then renames the old program file aside, because another program (File Explorer reading the icon) can hold it open with nothing running and the same check would stop the install or uninstall, and the app runs `cleanup_before_exit` before it hands over. Every release carries both installers, so `releases/latest/download/BorrowedCompute-setup.exe` and `…/BorrowedComputeAgent.dmg` are stable links to the newest. Local builds stay `0.1.0`, so any release counts as newer.

## Rules

- **Rust 1.91 is pinned** in `rust-toolchain.toml` because iroh 1.x requires it. Do not lower it.
- **Insecure relay TLS is test-only.** `NetConfig::insecure_relay_tls` exists only with `bc-net`'s `test-utils` feature. Never enable that feature in a non-dev dependency.
- **Jobs are `argv` arrays, never shell strings.** Keep it that way in the spec, wire format and runner.
- **Unknown `bc.toml` keys are errors** (`deny_unknown_fields`). Add new keys explicitly and validate them in `JobSpec::validate`.
- **Bump `PROTOCOL_VERSION` and `JOB_ALPN`** together on any incompatible change to `wire.rs`.
- **Never store provider tokens** (GitHub or Google). The cloud uses one once to read the user and their verified emails, then drops it. Session tokens are stored only as SHA-256.
- **Accounts are reached through identities** (`identities` table: provider + provider user id). A new identity joins the account of an existing identity with the same **verified** email, else creates an account (`account_for` in `auth.rs`). Never link on an unverified address. Google sign-in is offered only when a client id and secret are configured (`BC_GOOGLE_CLIENT_ID`/`BC_GOOGLE_CLIENT_SECRET`, or the Mac app's built-in id plus the `GOOGLE_CLIENT_SECRET` CI secret).
- **SQLite migrations run with foreign keys off** (`migrate_sqlite` in `bc-cloud`), then `pragma foreign_key_check`, because table rebuilds would otherwise cascade-delete sessions and devices. sqlx always wraps a SQLite migration in a transaction, so pragmas inside a migration file do nothing.
- **Device registration requires a signature** over `register_message` (bound to the session hash). Do not add a registration path without it.
- **Every cloud query is scoped by `account_id`.** v1 pairs only devices on the same account (Foundation decision; Q6).
- **Pairing codes are a secret between the requesting device and the person at the Mac.** Only `create` returns the code (to the requester); every list returns `code: None`, so the Mac owner must type it. Codes are 8 characters from an unambiguous alphabet, compared case- and dash-insensitively; three wrong codes delete the request (`pairings.attempts`). Approval must be signed by the Mac's device key over `approve_message` (pairing id, time, session hash): every device on the account has a session and the requesting PC holds the code, so a session alone would let a PC approve itself.
- **The account's device is found on the network, not typed.** The device that hosts the cloud, Mac or PC, advertises its endpoint over mDNS (`bc_net::lan`, iroh's `iroh-mdns-address-lookup` under the service name `borrowedcompute`), with `bc-host:<mac|windows>:<name>` as the endpoint's user data (older Macs send `bc-mac:<name>`, read as a Mac); `Agent::share_cloud` starts it with the computer name and the app renames it to the signed-in device name. Every app listens with an advertise-off lookup (`watch_nearby`, `nearby` events, `nearby_devices` command, leaving out its own id) and shows nearby devices with a Mac or PC label on the sign-in page and in the sidebar. Discovery only saves typing the device code: sign-in with the same account and the pairing code still decide who may run jobs. `cargo test -p bc-net --test lan -- --ignored` checks it on a machine with multicast.
- **Commands are written for the device that runs them** (`bc_cli::detect::Os`, from the device's `kind`; unknown, as for a shared Mac, counts as a Mac): suggestions and auto-fixes use `cmd /d /c`, `python` and `.venv\Scripts\` for a Windows PC, `sh -c`, `python3` and `.venv/bin/` otherwise; Swift and Xcode are offered only for a Mac, `gradlew.bat` and `.cmd`/`.ps1` scripts only for a PC. The app asks again when the selected device's system changes.
- **Mesh connections (`MESH_ALPN`, `borrowed-compute/mesh/2`) are for paired devices only**, while lending is on; guests never join a pipeline, because activations reveal the prompt. A stage accepts a feed from a device it never paired with only with a ticket signed by the coordinator that set the stage up (`ticket.rs`). Weights never travel over the mesh: each device fetches its own layers from the model's https address by byte range, into memory only (owner decision 2026-11-06: weights may stay in RAM while the model runs, never on disk), and drops them 2 minutes after its last stage ends. Model addresses from other devices must be https (plain http only to loopback), never file paths.
- **The agent checks the paired list on every connection.** It must never run a job from an unpaired device.
- **One device, one key, one endpoint.** A device that both lends and uses keeps one key. The agent registers its endpoint with `bc_net::share_endpoint`; `bc_net::bind` then hands that endpoint back for the same key instead of binding a second one (two endpoints with one key push each other off the relay, and `relay_only` does not apply to it), and the client code closes endpoints only through `bc_net::release`, which leaves the shared one open.
- **Lending is a switch** ("Lend this device", `Agent::set_lending`, saved in `<home>/lending`; on by default on a Mac, off on Windows). Off, the agent still serves the account's cloud but closes job and invite connections, and the app sends no heartbeats. Only lending devices send heartbeats, so the cloud lets a device be paired to only once it has checked in (`last_seen` set), and the app lists only those under Use.
- **The account lives on one device, any OS.** At first sign-in the "Where does your account live?" dialog picks a nearby device, takes a pasted code, or keeps it here (`keep_account_here`: writes `<home>/hosts-account`, starts `bc-cloud`, restarts the app if its agent already runs without it). A Mac from before the merge with `cloud/cloud.db` keeps hosting.
- **Guests are invited, never discovered.** A Mac can be shared with people on other accounts only through an invite: the owner turns on Share this Mac and creates one per person (`bc-invite:<Mac code>.<secret>`, single use, 7 days; `bc_proto::guest`). The guest's device presents it over `GUEST_ALPN` (`borrowed-compute/guest/1`, kept apart from the job protocol so nothing else changed), gets an 8-character code and waits on the same stream while the owner types the code on the Mac (three wrong tries cancel it). The cloud is not involved, so it keeps its single owner. Approved guests live in `<home>/guests.json` (invites only as SHA-256) and pass the per-connection check like paired devices while sharing is on. Turning sharing off or removing a guest stops their services. On the guest's side (`bc_cli::shared`, `bc join`, the PC app's Use a shared Mac) no sign-in is needed: joined Macs are kept in `<client home>/shared-macs.json` and `resolve_mac` finds them by name or id before asking any cloud, dialing them through iroh's discovery. The PC app shows its Mac list without an account when it has shared Macs. When the Mac hosts the cloud, jobs cannot connect to its port (`RunnerConfig::denied_ports`).
- **Packing fixes Windows files** (`apps/bc-cli/src/pack.rs`): executable bit from file system, git index (`100755`) or shebang for untracked files; CRLF to LF only in scripts. Do not normalize other text files.
- **Tests that need `sh` or the Mac agent are `cfg(unix)`**, so `cargo test --workspace` still runs on Windows CI.
- **Logs.** The Mac app writes `<home>/logs/agent.log` (its own stderr, unless run from a terminal) and one file per job in `<home>/logs/jobs/` (command, result, usage, and the job's output: the last 1 MB of stdout and stderr, from `AgentEvent::JobOutput`; newest 500 kept). The recent-jobs list is reloaded at startup from `<home>/agent/job-history.jsonl`. The client app writes each run's output and result to `<client home>/logs/job-<time>.log`, keeping the newest 200.
- **Job usage comes from `wait4`** in `runner.rs` (on Windows from the Job Object): CPU time and peak memory of the job's process plus every process it waited for. `AgentMsg::Exited.usage` is `#[serde(default)]`, so old and new clients and agents still talk without a protocol bump.
- **Jobs start from empty dependency caches** (`isolated_env` in `runner.rs`): `CARGO_HOME`, npm/pnpm/yarn/bun, pip/uv/poetry, Go, Gradle, Maven, NuGet, `XDG_CACHE_HOME` and `TMPDIR` all point into `<workspace>/cache`, set after the job's own env so a job cannot redirect them. Every build re-downloads its dependencies; that is the owner's zero-data choice, not a bug to optimize away. Installed toolchains stay where they are (`RUSTUP_HOME` is set explicitly so rustup still finds them). The uploaded project lives in `<workspace>/project`.
- **Jobs get the user's login-shell PATH** (`job_path` in `runner.rs`), asked once with `$SHELL -l -i`, because an app started from Finder only has `/usr/bin:/bin:/usr/sbin:/sbin` and would not find cargo, npm (nvm), Homebrew tools and the like.
- **Jobs run in a Seatbelt sandbox on macOS** (`apps/bc-agent/src/sandbox.rs`, through `/usr/bin/sandbox-exec`): read and write only the job's workspace; read system folders, Homebrew, Xcode and the user's toolchains (`.rustup`, nvm, pyenv…, plus PATH folders inside home); never the rest of home (`~/.cargo` beyond `bin` holds credentials). Outbound network allowed; a guest's jobs (`RunnerConfig::guest`, set for any device not on the paired list) reach only ports 80 and 443 off the Mac, because Seatbelt matches hosts only as `*` or `localhost` and cannot block the local network as such. Seatbelt's `localhost` also covers the Mac's own network addresses. Inbound only on localhost and on Unix sockets inside the workspace. When a tool breaks inside the sandbox, run `cargo run -p bc-agent --example sandbox_check` and widen the profile narrowly; `BC_NO_SANDBOX=1` on the agent turns it off for debugging.
- **Jobs run in an AppContainer on Windows** (`apps/bc-agent/src/sandbox_windows.rs`), one per job, inside a Job Object. The job's SID gets full access to its workspace; toolchain folders inside the profile (`.rustup`, `.cargo\bin`, Scoop, nvm, per-user Programs, PATH folders inside the profile) grant read and execute to the `borrowedComputeToolchains` capability, once, remembered in `<work root>/.toolchains`; everything else of the owner's is unreadable. Owner jobs get internet and local-network capabilities, guests internet only; AppContainers cannot reach the PC's localhost. The Job Object kills every process on exit, timeout and cancel and reports CPU time and peak committed memory. Services work through a relay: the agent cannot reach into an AppContainer over loopback, so each forwarded connection starts the agent's own program inside the job's AppContainer with `--bc-relay <port>` (`JobHandle::relay`, `helper_main` at the top of each `main`), which connects over loopback inside the container and pipes the connection over stdin and stdout; ports come from `GetExtendedTcpTable` for the Job Object's processes, and `SetThreadExecutionState` keeps the PC awake while a service runs. Inside the AppContainer cmd.exe runs a batch file only by a path relative to the job's folder (a full path gives "Access is denied", PATH finds nothing), so project scripts go relative, and batch files that only start a Node script (Node's `npm.cmd`/`npx.cmd`, npm's shims for global packages such as `yarn.cmd` and `pnpm.cmd`, Corepack's) run as `node.exe <script>` directly (`node_shim`); other batch files outside the job's folder do not run there. Node's module loader reads the attributes of every folder above each file it loads, from `C:\` down, which an AppContainer may not: the agent grants the toolchain capability read-attributes on each such folder itself (`open_folder_attributes`, through `SetFileSecurityW`, never `SetNamedSecurityInfoW`, which would walk the whole drive), and `C:\` and `C:\Users` need an administrator: the one-time setup (`--bc-setup`, run elevated by the installer on a fresh install and again when lending is turned on, if still needed) grants those and adds the app's "Borrowed Compute" firewall rule for private networks. Until then sandboxed jobs get `NODE_OPTIONS=--preserve-symlinks --preserve-symlinks-main` ahead of their own (`node_options`), which loads scripts but breaks symlinked packages. Windows does not let an AppContainer create junctions, which pnpm links packages with, so sandboxed jobs get `npm_config_node_linker=hoisted` (pnpm's flat, npm-like layout). Windows lending never runs a job outside the AppContainer except with `BC_NO_SANDBOX=1`. Its tests are `cfg(windows)` in `runner.rs` and run on Windows CI only.
- **Services** (`JobRequest.service`, `bc run --service`, the apps' Keep running checkbox) are owned by the agent's `Services` registry, not the connection: no timeout, they survive the client disconnecting, and they end only when the process exits or someone stops them (the starting device with `Stop`, or the Mac app for any). Only the starting device can list, attach to or stop its services. Recent output (256 KB) is kept in memory for attaching, never written to disk. While any service runs the agent holds `caffeinate -is -w <pid>`, so the Mac does not sleep (closing the lid on battery still sleeps it). Closing the connection detaches; `Cancel` on an attached stream stops the service.
- **Port forwarding** (`apps/bc-cli/src/forward.rs`, `forward` in `server.rs`): a service's ports reach the client's `127.0.0.1` at the same port (another when taken), one QUIC stream per TCP connection after `Forward`/`Connect`. The agent forwards only ports the service's own process group listens on (`lsof -g <pgid>`), never anything else on the Mac's localhost. The Windows app forwards while a selected Mac has services; the CLI while `bc run --service` is watched, or with `bc forward`. Detection marks dev/start/serve/preview scripts and HTML Serve as services.
- **The Mac's cloud has one owner.** The built-in cloud runs with `single_owner`: once an account exists, a sign-in that would create another is refused (403). Any cloud refuses new sign-ins while 20 are in progress (429), because each asks GitHub or Google for a code. The agent serves at most 32 cloud connections at once, 16 requests each. Before the paired or invite check, job and guest connections are capped too (`MAX_HANDSHAKES` in `server.rs`: 64 at once, frames up to 1 MiB through `recv_msg_max`, 30 seconds), because anyone with the Mac code can open them. A separately deployed cloud sets `BC_SINGLE_OWNER` to get the same lock.
- **Forwarding never flickers.** Only a poll the Mac answers that no longer lists a service closes its local ports; a failed poll changes nothing, and a dropped service connection reconnects behind the same listeners (`watch` channel). In the PC app the forwarding task is the only source of the service list (`services` events with the Mac's name), started for any approved Mac and stopped only for an unpaired one, so one endpoint polls instead of a new endpoint and cloud lookup per check.
- **The Mac's cloud travels over iroh.** The agent's endpoint accepts `CLOUD_ALPN` (`borrowed-compute/cloud/1`) from any device, paired or not (sign-in and pairing come first), and pipes each stream to the cloud on `127.0.0.1:8080`, nothing else. A device's cloud address `iroh://<Mac endpoint ID>` (the "Mac code"; `normalize_cloud_url` accepts the bare code, and plain `http` only for localhost, since session tokens ride on every request) makes `CloudClient` send requests through a local proxy from `bc_net::cloud_proxy`. No Tailscale and no relay of the Mac's own: devices use iroh's public relays and discovery. A cloud deployed elsewhere can still advertise a relay (`BC_RELAY_URL`, `GET /v1/relay`). `BC_TEST_RELAY_URL` runs `job_messages_flow_through_a_deployed_relay` against a real deployment.
- **Workspaces are deleted after every job**, and the job's process group is killed on exit, timeout and cancel (`GroupGuard` in `runner.rs`). Keep both guarantees.
- **Desktop apps call the libraries, never the CLI binaries.** New client or agent behavior goes in `bc_cli::flows` or `bc_agent::service` first, then both the CLI and the app use it.
- **Never use `confirm()`, `alert()` or `prompt()` in the desktop UIs.** The web view has no native handler for them on macOS (the Mac app's `confirm()` returned "no" without showing anything). Use `ask()` in each `ui/app.js`.
- **Text colors must pass WCAG AA (4.5:1) in light and dark mode.
- **Appearance is the app's choice, not only the system's.** `ui/theme.js` (loaded in `<head>` before CSS so there is no flash) sets `data-theme` to `light` (default), `dark` or `system`; base.css holds the light tokens in `:root` and keys dark tokens on `[data-theme="dark"]` and on `[data-theme="system"]` inside `prefers-color-scheme: dark`.
- **The visual system is in `DESIGN.md`** (product context in `PRODUCT.md`), by the owner's decision; no themed metaphors. Geist and Geist Mono are bundled in `ui/fonts/` (OFL), with system fonts as fallbacks. Ink is the one accent, black in light mode and near-white in dark, never purple or indigo. Anything filled with the accent uses `--on-accent` for its text or knob. Both sidebars hold Use (devices, running servers) and This device (Overview, Activity, Paired devices, Sharing, Settings; `showPage` in `lend.js`, remembered in `localStorage`). Shared motion lives in `ui/motion.js`: one sliding sidebar highlight, page entrances, the large title handing off to the frosted bar, count-ups and the ⌘K/Ctrl+K command palette. Keyboard-started changes never animate. The Overview's core grid polls `cpu_load` (`sysinfo`, whole-computer per-core use) once a second, only while a run or server is up and the window is visible. Some class names (`coupon`, `legs`, `jet`, `stamp`) are kept from earlier looks so the apps' code did not change.
- **The agent window re-renders only what changed** (`setHtml` in its `app.js`), so the 5-second poll never resets focus or replays animations. Keep new lists on that path.
- Cloud SQL uses runtime `sqlx::query`/`query_as`, not compile-time macros, so builds need no database.
- **Cloud SQL must run on SQLite and Postgres.** No database-side time (`now()`, intervals): pass Unix seconds from `bc_cloud::now()`. Number `$N` parameters in order of first use. Keep both migration folders describing the same schema. Tests run every API test on SQLite.
- **The apps read the session from disk on every call** (`AppState::cloud()`), so the CLI and the app stay one device. A 401 means the session belongs to another cloud: sign out locally and show sign-in.
- Write code comments and docs in plain prose: why, not what.

## Known gaps (Phase one)

- `bc` cannot cross-compile for Windows from macOS (`ring` needs Windows SDK headers). `.github/workflows/windows.yml` builds `bc.exe` and runs the Windows-capable tests on `windows-latest`. A real job from a Windows PC to a Mac is still untested.
- Jobs run inside a Seatbelt sandbox but still as the agent's user; the separate `_bcjob` user needs a root helper and Developer ID signing (Phase two, Q4).
- The whole project is uploaded per run (up to 20 GiB, `MAX_ARCHIVE_BYTES`; `.git` and `node_modules` are never sent), by design: the owner decided the Mac stores zero project data, so there is no Mac-side cache or chunked sync (Foundation doc, 2026-10-25). Both sides hold the archive in a temporary file, never in memory. Compressed uploads (zstd) are the planned speed-up.
- **Route memory** (`apps/bc-cli/src/route.rs`): when a direct path to a Mac fails, the client records it in `route-memory.json` and sends that Mac's runs through the relay first for an hour, or until the Mac's IP addresses change, or until a direct run succeeds.
- Discovery and relays are iroh's public ones unless a separately deployed cloud advertises its own relay.
- The cloud over iroh is tested with a stand-in cloud, locally and through public discovery (`cargo test -p bc-net --test cloud -- --ignored`); not yet from a real second device.
- The desktop apps are verified on macOS only. CI builds the Windows installers, but nobody has run them on a Windows PC yet.
- The Mac agent app is ad-hoc signed (`bundle.macOS.signingIdentity: "-"`), not Developer ID signed or notarized, so a downloaded copy needs System Settings › Privacy & Security › Open Anyway once. Without the bundle signature macOS calls the download "damaged". It does not start at login yet. Updates installed by the app are not quarantined, so they open directly.
