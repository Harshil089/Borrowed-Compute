How it works

Everything from the first install to a dev server running on another computer of yours at this one's localhost. About ten minutes the first time, a single click every time after.

On this page Overview Set up Run a job bc.toml Dev servers Sharing Command line Security Updates Troubleshooting

Overview

Borrowed Compute is one app, the same on a Mac and a PC. Under Use you choose a project folder, type a command and watch the output while it runs on another computer of yours. Under This device you lend this computer to your others: approve devices, see what ran, and turn lending on or off. It works in every direction: PC to Mac, Mac to PC, Mac to Mac and PC to PC.

For every run, your computer packs the project and sends it with the command over an encrypted connection. The computer that lends runs it with its own native toolchain in a fresh, sandboxed workspace. Output streams back as it is printed. When the job ends, the workspace and every dependency it downloaded are deleted. No program built on one system ever runs on the other, and nothing from your project stays behind.

Set up

On the first computer

  1. Download the app: BorrowedComputeAgent.dmg for a Mac (drag it to Applications), BorrowedCompute-setup.exe for a PC.
  2. The first time, macOS blocks the app because it is not notarized yet: open System Settings, then Privacy & Security, and click Open Anyway. On Windows, if SmartScreen warns, choose More info, then Run anyway; Windows then asks once to let the app set up its sandbox and firewall rule.
  3. Sign in with GitHub or Google, and choose Keep the account on this device. This computer now hosts your account: there is no separate server.
  4. Under This device, turn on Lend this device if your other computers should run jobs here. It is on by default on a Mac.

On each other computer

  1. Install the same app and open it.
  2. When it asks where your account lives, pick the first computer from the list of devices on this network, or paste its code from that computer's This device page. Then sign in with the same account.
  3. Click Pair next to the computer you want to run on. Your screen shows an eight-character code.
  4. On that computer, type the code into the request and click Approve.

Why a codePairing codes are a secret between the computer asking and the person at the one lending. They expire after ten minutes, and three wrong tries delete the request.

Run a job

Choose a computer under Use, choose a project folder, then type a command or pick one of the suggestions for that folder. Press Run.

  • Your project is packed and uploaded. node_modules, .venv, target and other build output are left out.
  • Suggestions and fixes are written for the computer that runs them: sh and .venv/bin on a Mac, cmd and .venv\Scripts on a PC.
  • If the command needs what was left out, it installs dependencies or builds first. After a failure caused by a missing module, command or build file, it fixes the cause and runs once more.
  • Files from Windows are fixed while packing: scripts get their executable bit and LF line endings back. Binaries and other text files are sent unchanged.
  • When it ends you see the exit code, timings (connect, upload, first output, total, direct or relay) and what the job used: CPU time, cores and peak memory.

Each run's output is saved on your computer. The lending computer keeps the command, result, usage and the last 1 MB of output for each job in its log.

bc.toml

A bc.toml in your project folder always wins over detection. Commands are lists of arguments, never shell strings, and unknown keys are errors so a typo never silently does nothing.

# bc.toml
version = 1

[job]
argv = ["cargo", "test", "--workspace"]
workdir = "."
timeout = "20m"
service = false     # true keeps a server running

[job.env]
RUST_LOG = "info"

[files]
exclude = ["data/raw"]

Dev servers

Tick Keep running, which is ticked for you for dev, start and serve scripts, and the server stays up on the lending computer until you press Stop. It survives your computer disconnecting, and the lending computer stays awake while it runs.

Every port the server listens on opens at the same address on your computer, so a Vite server on the other computer's port 5173 is at http://localhost:5173 on yours. Only the server's own ports are forwarded, never anything else on the lending computer. Ports reconnect quietly when the network drops.

Sharing

You can let people on other accounts run jobs on one of your computers, one invite per person. A guest needs no account of their own.

If someone invited you

  1. Install Borrowed Compute.
  2. Open it and choose Use a shared device, or Join shared once you are signed in.
  3. Paste the whole invite, starting with bc-invite:, and click Join.
  4. Your screen shows a code. Read it to the person who invited you; they type it on their computer.
  5. Once they approve, their computer appears in your list, marked as shared. Run on it like any other.

If you are sharing your computer

  1. Under This device, in Sharing, turn on Share this device.
  2. Type the person's name and click Invite, then copy the message and send it by chat or email. It is shown only once.
  3. When their request arrives, type the code their screen shows and click Approve.

LimitsEach invite works once, within seven days. Three wrong codes cancel the request. Guests run in the same sandbox as your own jobs, with less network access, the same limits per device, and see only their own servers. Turning sharing off, or removing a guest, stops their servers at once.

Command line

The bc command does everything the app's Use pages do and shares its device identity, so pairing once covers both.

bc cloud <device code>       # where your account lives
bc login                     # --google for Google
bc pair studio               # shows a code; approve it on studio
bc use studio                # default computer for bc run

bc run -- cargo test         # --timings, --relay-only
bc run --service -- npm run dev
bc services                  # servers this device started
bc attach <id>               # watch one; Ctrl+C stops watching only
bc forward                   # forward their ports to localhost
bc stop <id>

Security

A job is your code plus every package it installs, so the lending computer treats it as untrusted.

  • Sandboxed on a Mac. Each job runs in a macOS sandbox. It can read and write its own workspace and read system folders and your toolchains (Homebrew, rustup, nvm, pyenv, Xcode). It cannot read the rest of your home folder, the clipboard, the keychain or other apps' settings, cannot open apps, and cannot reach your ssh agent or well-known local services such as PostgreSQL, Redis, Docker or Ollama.
  • Sandboxed on a PC. Each job runs in its own Windows AppContainer inside a Job Object. It can read and write its own workspace and read Windows, Program Files and your toolchains (rustup, nvm, Scoop, per-user installs). It cannot read the rest of your profile, cannot reach services on the PC's own localhost, and every process it starts ends with it.
  • Nothing stays. The workspace, including every downloaded dependency, is deleted when the job ends, and its processes are stopped. Each run starts from empty caches.
  • Only your devices. Only devices signed in to your own account can ask to pair, and only after you approve a code. The built-in sign-in accepts only its owner's account.
  • Limits. One device can run at most four jobs and keep eight servers at once, and refused devices are logged at most every ten minutes.
  • Encrypted. Devices connect over QUIC with their own keys. When a direct path is not possible, a relay forwards traffic it cannot read.
  • Secrets. Sign-in sessions and device keys live in the system keychain or Windows Credential Manager. GitHub and Google tokens are used once at sign-in and dropped.

Known limitsJobs still run as your own user inside the sandbox; a separate job user is planned. The Mac app is not notarized and the Windows installer is not code-signed yet.

Updates

The app checks for a newer release when it starts and install it, so an older installer always ends up on the latest version. Check for updates does the same on demand. Every update is verified against the project's signing key before it installs, and dropped downloads are retried.

Troubleshooting

macOS says the app is damaged or can't be opened

Open System Settings, then Privacy & Security, and click Open Anyway. If macOS still refuses, clear the download flag in Terminal:

xattr -dr com.apple.quarantine "/Applications/Borrowed Compute Agent.app"

Windows SmartScreen blocks the installer

Choose More info, then Run anyway. The installer is not code-signed yet.

Your computer can't find the other one

Check that Borrowed Compute is open on the other computer, or that Run in background is on there, that Lend this device is on, and that the code you entered matches the one on its This device page. On strict networks the connection goes through a relay automatically.

A tool works in a terminal but not in a job

Jobs use your own PATH and can read your toolchains, but not the rest of your home folder. If a tool keeps its files elsewhere in your home folder, it cannot see them from the sandbox.
