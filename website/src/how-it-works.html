How it works

Everything from the first install to a dev server running on your Mac at your PC's localhost. About ten minutes the first time, a single click every time after.

On this page Overview Set up Run a job bc.toml Dev servers Command line Security Updates Troubleshooting

Overview

Borrowed Compute is two apps. Borrowed Compute runs on your Windows PC: you choose a project folder, type a command and watch the output. Borrowed Compute Agent runs on your Mac: it signs you in, approves devices, runs each job and shows what ran.

For every run, the PC packs your project, sends it with the command over an encrypted connection, and the Mac runs it with its own native arm64 toolchain in a fresh workspace. Output streams back as it is printed. When the job ends, the workspace and every dependency it downloaded are deleted. No Windows program ever runs on the Mac, and nothing from your project stays there.

Set up

On the Mac

  1. Download BorrowedComputeAgent.dmg, drag the app to Applications and open it.
  2. The app is not notarized yet, so macOS blocks it the first time. Open System Settings, then Privacy & Security, and click Open Anyway.
  3. Sign in with GitHub or Google. Your Mac now hosts your account: there is no separate server.
  4. Under Route, copy this Mac's code.

On the PC

  1. Install BorrowedCompute-setup.exe. If SmartScreen warns, choose More info, then Run anyway.
  2. Paste the Mac's code where the app asks for your Mac, click Test, then sign in with the same account as on the Mac.
  3. Click Pair next to your Mac. The PC shows an eight-character code.
  4. On the Mac, type that code into the request and click Approve.

Why a codePairing codes are a secret between the PC and the person at the Mac. They expire after ten minutes, and three wrong tries delete the request.

Run a job

Choose a project folder, then type a command or pick one of the suggestions for that folder's project type. Press Run on Mac.

  • Your project is packed and uploaded. node_modules, .venv, target and other build output are left out.
  • If the command needs what was left out, it installs dependencies or builds first. After a failure caused by a missing module, command or build file, it fixes the cause and runs once more.
  • Windows files are fixed while packing: scripts get their executable bit and LF line endings back. Binaries and other text files are sent unchanged.
  • When it ends you see the exit code, timings (connect, upload, first output, total, direct or relay) and what the Mac used: CPU time, cores and peak memory.

Each run's output is saved on the PC. The Mac keeps the command, result, usage and the last 1 MB of output for each job in its log.

bc.toml

A bc.toml in your project folder always wins over detection. Commands are lists of arguments, never shell strings, and unknown keys are errors so a typo never silently does nothing.

# bc.toml
version = 1

[job]
argv = ["cargo", "test", "--workspace"]
workdir = "."
timeout = "20m"
service = false     # true keeps a server running

[job.env]
RUST_LOG = "info"

[files]
exclude = ["data/raw"]

Dev servers

Tick Keep running, which is ticked for you for dev, start and serve scripts, and the server stays up on the Mac until you press Stop. It survives the PC disconnecting, and the Mac stays awake while it runs.

Every port the server listens on opens at the same address on your PC, so a Vite server on the Mac's port 5173 is at http://localhost:5173 on Windows. Only the server's own ports are forwarded, never anything else on the Mac. Ports reconnect quietly when the network drops.

Command line

The bc command does everything the PC app does and shares its device identity, so pairing once covers both.

bc cloud <mac code>          # where your Mac is
bc login                     # --google for Google
bc pair studio               # shows a code; approve it on the Mac
bc use studio                # default Mac for bc run

bc run -- cargo test         # --timings, --relay-only
bc run --service -- npm run dev
bc services                  # servers this device started
bc attach <id>               # watch one; Ctrl+C stops watching only
bc forward                   # forward their ports to localhost
bc stop <id>

Security

A job is your code plus every package it installs, so the Mac treats it as untrusted.

  • Sandboxed. Each job runs in a macOS sandbox. It can read and write its own workspace and read system folders and your toolchains (Homebrew, rustup, nvm, pyenv, Xcode). It cannot read the rest of your home folder, the clipboard, the keychain or other apps' settings, cannot open apps, and cannot reach your ssh agent or well-known local services such as PostgreSQL, Redis, Docker or Ollama.
  • Nothing stays. The workspace, including every downloaded dependency, is deleted when the job ends, and its processes are stopped. Each run starts from empty caches.
  • Only your devices. Only devices signed in to the Mac's own account can ask to pair, and only after you approve a code. The Mac's built-in sign-in accepts only its owner's account.
  • Limits. One device can run at most four jobs and keep eight servers at once, and refused devices are logged at most every ten minutes.
  • Encrypted. Devices connect over QUIC with their own keys. When a direct path is not possible, a relay forwards traffic it cannot read.
  • Secrets. Sign-in sessions and device keys live in the system keychain. GitHub and Google tokens are used once at sign-in and dropped.

Known limitsJobs still run as your own macOS user inside the sandbox; a separate job user is planned. The Mac app is not notarized and the Windows installer is not code-signed yet.

Updates

Both apps check for a newer release when they start and install it, so an older installer always ends up on the latest version. Check for updates does the same on demand. Every update is verified against the project's signing key before it installs, and dropped downloads are retried.

Troubleshooting

macOS says the app is damaged or can't be opened

Open System Settings, then Privacy & Security, and click Open Anyway. If macOS still refuses, clear the download flag in Terminal:

xattr -dr com.apple.quarantine "/Applications/Borrowed Compute Agent.app"

Windows SmartScreen blocks the installer

Choose More info, then Run anyway. The installer is not code-signed yet.

The PC can't find the Mac

Check that Borrowed Compute Agent is open on the Mac, or that Run in background is on, and that the code on the PC matches the one under Route on the Mac. On strict networks the connection goes through a relay automatically.

A tool works in Terminal but not in a job

Jobs use your login shell's PATH and can read your toolchains, but not the rest of your home folder. If a tool keeps its files elsewhere in your home folder, it cannot see them from the sandbox.
